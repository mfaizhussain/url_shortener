01

        

          
The viral post that killed the database

          
Start with the problem: lakhs of people reading the same data at the same time

        

      


      
Picture a social app built with Express and MongoDB, the kind you have already built in class. Users write posts. Others read, like and comment. Every time someone opens a post, the server runs Post.findById(id) and sends the result back.

      
One evening, a student from Bhopal posts a meme about exam results. It gets forwarded on WhatsApp groups and Instagram stories. Within ten minutes, 2 lakh people open the same post. Step through what happens to the server.


      

        
Step-throughFrom a quiet evening to a crashed database

        

          
        

        

          
Requests / sec≈ 1

          
DB connections3 / 100

          
Response time20 ms

          
StatusHealthy

        

        

          
    
            
  1. A normal evening
    About 50 people open post #42 per minute. Each view sends one request to Express, which runs one MongoDB query. The connection pool is almost empty and responses take ~20 ms.
    2. 
            
  2. The post goes viral
    The meme gets forwarded everywhere. Suddenly 2,00,000 people open it within a minute, about 3,300 requests every second, all for the same URL: GET /posts/42.
    3. 
            
  3. Same question, asked again and again
    Look at what each request asks the database: Post.findById(42). The caption, image and author haven't changed, so every one of those queries returns exactly the same document. The database still does the full work every single time.
    4. 
            
  4. Connections run out
    The pool has 100 connections. All 100 are busy, so new queries wait in a queue. Response time climbs from milliseconds to seconds. People see a spinner and hit refresh, which sends even more requests. This is called a retry storm.
    5. 
            
  5. The database falls over
    CPU is pinned at 100%, the queue overflows and queries time out. Every feature shares this database, so login, feed and notifications go down too, not just the viral post.
    6. 
            
  6. The real problem
    We are reading the same unchanged data from the most expensive place we have, lakhs of times. What we need is a ready copy kept somewhere much cheaper to read, close to our servers. That copy is called a cache.
    7. 
          

        

      


      

        
Key Concept

        
A read-heavy hotspot is a small piece of data that a huge number of users read at the same moment. The data barely changes, but the database pays the full price for every read. Product pages during a sale, results day, IPL live scores and trending posts are all read-heavy hotspots.

      


      

        
Quiz · 01

        
In the viral post story, what actually crashed the database?

One hot route starves a shared resource, and every other route that needs that resource starts timing out as well.

Why the database chokes

          
Work per read, connection pools, and the simple math behind the crash

        

      


      
Every read is real work

      
A database is built to store data safely on disk and to answer any question you can ask about it. That flexibility costs work on every query, even a simple findById. Watch both pipelines run. Each lit chip is one stage of work.

The connection pool is a fixed number of counters

      
Your Node app doesn't open a fresh database connection per request. It keeps a pool. The MongoDB Node driver (which Mongoose uses) defaults to maxPoolSize: 100, and PostgreSQL defaults to max_connections = 100. A query holds one connection until it finishes. When all of them are busy, the next query waits in a queue.


      

        
Analogy

        
Think of a bank branch with a fixed number of counters and a token machine. If customers arrive faster than counters free up, the waiting hall fills. People who give up and come back (users hitting refresh) make the line even longer.

      


      
Do the math

      
The rough ceiling of any pool is connections ÷ time per query. With 100 connections and 20 ms per query, that's 100 ÷ 0.020 = 5,000 queries per second on a good day. A post page usually needs more than one query (post, author, top comments, "did I like this?"). Move the slider to see what viral traffic does to that ceiling.

So we want a copy of hot data that is (1) far cheaper to read than the database, (2) shared by every server instance we run, and (3) able to forget old data on its own. That's exactly the job Redis was built for.


      

        
Quiz · 02

        
A pool has 100 connections and each query takes 50 ms. Roughly how many queries per second can it serve at best?

Quiz · 02

        
When database utilisation goes past 100%, what happens to response time?

        

          
          
        

        

        
If more work arrives per second than the system can finish, the queue never drains. Every second adds more waiting requests.

      

    


    
    

      

        
03

        

          
Enter Redis

          
An in-memory data structure store that every server can share

        

      


      

        
Key Concept

        
Redis (REmote DIctionary Server) is a server that keeps data in RAM and lets you read and write it over the network by key. Picture a giant JavaScript Map running in its own process, which every one of your Node servers can talk to.

      


      

        
☕

        
The chai tapri analogy. Brewing a fresh cup for every customer takes four minutes: boil water, add leaves, milk, sugar. That's a database query. A smart chaiwala keeps a big kettle of ready chai on the counter and pours in seconds. That's a cache. After half an hour the kettle chai goes cold and he makes a new batch (that's TTL, Section 6). If he changes the recipe but the kettle still has the old batch, customers get the old taste (that's stale data, Section 7).

      


      
Where Redis sits

      

        

          
        

      


      
Why Redis is so fast

      
    
        
  • Data lives in RAM. No disk seek on the read path. A main-memory reference is around 100 ns, while an SSD random read is around 100 µs, roughly a thousand times slower.
    • 
        
  • Simple structures with known cost. GET is a hash-table lookup, O(1). There's no query parser or planner deciding what to do.
    • 
        
  • One thread runs the commands. Commands execute one at a time, so there are no locks, and every single command is atomic. That property powers rate limiters and leaderboards later.
    • 
        
  • Event-loop networking. Like Node.js, one thread handles thousands of client connections with I/O multiplexing. A single small instance can usually serve tens of thousands to over a hundred thousand simple operations per second.
    • 
      


      
"Why not just use a JavaScript Map?"

      
Every student asks this. A Map inside your Node process works on your laptop and then falls apart in production.

      

        

          
WhatIn-process MapRedis

          
            
Shared across serversNo. Each PM2 worker or Kubernetes pod has its own copy.Yes. One store that every instance reads ✓

            
Survives an app restart / deployNo. It's gone on every deploy.Yes. Redis is a separate process ✓

            
ExpiryDIY with setTimeoutBuilt in: EX, EXPIRE, TTL ✓

            
Memory limitsGrows the Node heap and causes GC pausesmaxmemory + eviction policies ✓

            
Atomic counters across serversImpossibleINCR, ZINCRBY, MULTI ✓

            
Data structuresWhatever you code yourselfStrings, hashes, lists, sets, sorted sets, streams, Pub/Sub ✓

          
        

      


      

        
⚠️

        
RAM is expensive and limited. Used as a cache, Redis is not your source of truth. Keep the real data in MongoDB or Postgres and treat Redis as a fast copy you can afford to lose. Redis can persist to disk (RDB snapshots, AOF logs), but caching code should still work if the cache comes back empty.

      

      

        
💡

        
In production you'll often use a managed service such as AWS ElastiCache, Redis Cloud or Upstash. Valkey is an open-source fork of Redis that speaks the same protocol. ioredis works with all of them.

      


      

        
Quiz · 03

        
Redis runs commands one at a time on a single thread. What does that give us?

        

          
          
        

        

        
Two servers running INCR on the same key at the same moment will always get 1 and 2, never 1 and 1.

      

      

        
Quiz · 03

        
You run 4 Express instances with PM2 and cache posts in a JS Map. Post 42 is cached in instance 1, and the next request lands on instance 3. What happens?

        

          
          
        

        

        
Processes don't share memory. That's the main reason a shared cache like Redis exists.

05

        

          
Caching with the cache-aside pattern

          
Check Redis first, fall back to the database, keep a copy for the next reader

        

      


      
The most common caching pattern is cache-aside, also called lazy loading. Your application sits in the middle and talks to both Redis and the database. Redis never talks to the database itself. Data only goes into the cache after somebody actually asks for it.


      

        
Step-throughOne miss, then hits for everyone else

        

          
        

        

          
    
            
  1. A request arrives
    A reader opens /posts/42. Express calls our getPost(42) function.
    2. 
            
  2. Ask Redis first
    Before touching the database, the server sends GET post:42 to Redis. That's a hash lookup in RAM.
    3. 
            
  3. Cache miss
    Nobody has asked for this post since the cache was last empty, so Redis replies (nil). ioredis gives us null.
    4. 
            
  4. Fall back to the database
    The server runs the normal query Post.findById(42). This is the slow, expensive path.
    5. 
            
  5. Keep a copy, with an expiry
    When MongoDB returns the document, the server stores it in Redis: SET post:42 <json> EX 60. The EX 60 means "delete this copy in 60 seconds" (Section 6).
    6. 
            
  6. Respond (the slow path happens once)
    The first reader waited ~41 ms. That's the full cost, paid by just one request.
    7. 
            
  7. The next reader gets a cache hit
    Another user opens the same post. GET post:42 now returns the JSON. That's a cache hit.
    8. 
            
  8. Fast response, idle database
    The response takes ~2 ms and MongoDB isn't touched. One DB query now serves every reader until the key expires. That's how a viral post stops being a DB problem.
    9. 
          

        

      


      
The code

      

        
services/post.service.js


import { redis } from "../lib/redis.js";
import Post from "../models/post.model.js";

const POST_TTL = 60; // seconds

export async function getPost(postId) {
  const key = `post:${postId}`;

  // 1. Try the cache first
  const cached = await redis.get(key);
  if (cached) return { post: JSON.parse(cached), source: "HIT" };

  // 2. Miss → ask the database
  const post = await Post.findById(postId).lean();
  if (!post) return { post: null, source: "MISS" };

  // 3. Keep a copy for the next reader, with an expiry
  await redis.set(key, JSON.stringify(post), "EX", POST_TTL);
  return { post, source: "MISS" };
}

      

      

        
routes/post.routes.js


router.get("/posts/:id", async (req, res) => {
  const { post, source } = await getPost(req.params.id);
  res.set("X-Cache", source);              // handy while debugging: HIT or MISS
  if (!post) return res.status(404).json({ message: "Post not found" });
  res.json(post);
});

Hit ratio = hits ÷ (hits + misses). At 95%, only 5 out of every 100 reads reach the database. For a hot key like our viral post, the hit ratio gets close to 100% after the first request.

06

        

          
TTL: giving data an expiry date

          
How Redis forgets things on its own, and how to choose how long to remember

        

      


      
TTL (time to live) is a countdown attached to a key. When it reaches zero, Redis deletes the key. TTL does two jobs at once: it caps how stale a cached copy can get, and it frees memory automatically so the cache doesn't grow forever. Back at the chai tapri, it's the rule "make a fresh kettle every 30 minutes".


      

        
InteractiveTTL laba tiny Redis running in your browser

⚠️

        
A plain SET wipes the TTL. If post:42 had EX 60 and you run SET post:42 newValue without EX, the key now lives forever (TTL → -1). Always pass EX again, or use KEEPTTL. INCR is different: it keeps the existing TTL.

      


      

        
💡

        
How Redis actually expires keys: lazily (it checks the expiry whenever you access a key) and actively (a background job samples keys that have TTLs about 10 times a second and deletes expired ones). An expired key is never returned to you, but it may take a moment to leave memory.

      


      
Choosing a TTL

      
There's no magic number. A short TTL keeps data fresher but sends more traffic to the DB. A long TTL protects the DB but shows older data. Decide per kind of data:

      

        

          
DataTypical TTLWhy

          
            
Viral post body60 – 300 sRarely edited. Even 60 s turns lakhs of reads into one query a minute.

            
Like / view counts5 – 10 sNobody notices if a count is a few seconds behind.

            
Public user profile10 – 30 minChanges rarely. Delete it on edit (Section 7).

            
Feature flags / config30 s – 5 minRead on every request. Short enough that a change rolls out quickly.

            
OTP5 minHere the TTL is a security rule, not a performance setting.

            
Rate-limit window= windowThe TTL is the window (Section 12).

07

        

          
The first new problem: stale data

          
Every cache is a copy, and copies go out of date

        

      


      
Every solution in tech brings its own problems. Caching fixed the crash, but now the same data lives in two places, MongoDB and Redis, and nothing forces them to agree. When the author edits the post, MongoDB has the new caption while Redis keeps serving the old one. Readers get stale data.


      

        
Step-throughHow a cache goes stale, and the fix

        

          
        

        

          
    
            
  1. Everything is in sync
    The post is cached with a 300-second TTL. Redis and MongoDB both say "Hello Bhopal". Readers get fast cache hits.
    2. 
            
  2. The author edits the caption
    PATCH /posts/42 updates MongoDB to "Hello Indore". Our update code only touches the database.
    3. 
            
  3. Readers get the old copy
    The next GET post:42 is still a hit. The old JSON is in Redis with 247 seconds left, and Redis has no way to know the database changed.
    4. 
            
  4. Stale until the TTL runs out
    For up to 5 minutes, every reader sees the old caption. On a viral post that's tens of thousands of wrong responses. The TTL is the maximum staleness, which is why it should never be "forever".
    5. 
            
  5. Fix: delete the key when you write
    After updating MongoDB, the server runs DEL post:42. The stale copy is gone right away.
    6. 
            
  6. The next read refills with fresh data
    The next reader misses, the server reads the new document from MongoDB and caches it again. Everyone sees "Hello Indore".
    7. 
          

        

      


      
Try it: edit the post and watch readers

      
Send a few requests so the post gets cached, then edit the caption in the DB. With TTL only, responses stay stale until the key expires. Switch to DEL on write and edit again.

      


      
Invalidation strategies

      

        

          
StrategyHowFreshnessThe catch

Order matters: update the DB, then delete the cache

      
It looks harmless to delete the cache first. Here's the race that bites you when a reader slips in between:

      

        
Writer: DEL post:42
Cache is empty. The DB update hasn't happened yet.

        
Reader: GET post:42 → miss
Goes to the database…

        
Reader: reads the old document from MongoDB
The writer's update is still in flight.

        
Writer: updateOne(...) finishes
The DB now has the new caption.

        
Reader: SET post:42 <old> EX 300
The old value is cached for 5 minutes, even though we "invalidated".

      

      
Updating the DB first and deleting afterwards shrinks this window to almost nothing. Keep a TTL anyway, as a safety net for the rare race that still slips through.

export async function updatePost(postId, changes) {

  const post = await Post.findByIdAndUpdate(postId, changes, { new: true }).lean();

  // 2. Then remove every cached copy that contains this post
  await redis.del(`post:${postId}`, `user:${post.author}:posts`);

Cache stampede: when the hot key expires

          
Thousands of requests miss at the same moment and run the same query together

        

      


      
Back to our viral post, cached with a 60-second TTL. At second 60 the key disappears, and thousands of requests are in flight at that instant. They all check Redis, all get nil, and all run the same DB query. It's the exact crash from Section 1, triggered by our own TTL. This is called a cache stampede (also thundering herd or dog-piling).

Fix 1 — Let only one request rebuild (mutex lock)

      
Redis can act as a lock because SET … NX ("only set if the key does Not eXist") is atomic. Out of thousands of simultaneous requests, exactly one gets "OK". Everyone else gets null.

      

        
services/post.service.js · stampede-safe


import { randomUUID } from "node:crypto";
import { redis } from "../lib/redis.js";
import Post from "../models/post.model.js";

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// Delete the lock only if WE still own it (compare-and-delete, atomic in Lua)
const RELEASE_LOCK = `
  if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
  end
  return 0
`;

export async function getPostSafe(postId, attempt = 0) {
  const key = `post:${postId}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  const lockKey = `lock:${key}`;
  const token = randomUUID();
  const gotLock = await redis.set(lockKey, token, "PX", 5000, "NX"); // "OK" or null

  if (gotLock === "OK") {
    try {
      const post = await Post.findById(postId).lean();      // only ONE request does this
      if (post) await redis.set(key, JSON.stringify(post), "EX", 60);
      return post;
    } finally {
      await redis.eval(RELEASE_LOCK, 1, lockKey, token);
    }
  }

  // Someone else is rebuilding: wait a little, then read the cache again
  if (attempt >= 20) return Post.findById(postId).lean();   // give up after ~1 s
  await sleep(50);
  return getPostSafe(postId, attempt + 1);
}

Fix 2 — Merge duplicate misses inside one server (single-flight)

      
Within one Node process you don't even need Redis for this. Keep the in-progress Promise and let concurrent callers wait on it. That turns 1,000 identical misses on one server into one DB query. Combine it with the Redis lock to also cover requests on other servers.

const inflight = new Map(); // key -> Promise

export function singleFlight(key, loader) {
  if (inflight.has(key)) return inflight.get(key);         // join the request already running
  const p = loader().finally(() => inflight.delete(key));
  inflight.set(key, p);
  return p;
}

// usage
const post = await singleFlight(`post:${id}`, () => getPostSafe(id));

      


      
Fix 3 — Refresh before it expires (stale-while-revalidate)

      
For the hottest keys, never let readers see a miss. Store a "fresh until" time inside the value and give the Redis key a longer real TTL. When a reader finds data that's past its fresh time, it still returns that slightly old copy right away and starts one background refresh, protected by the same lock.

      

        
services/post.service.js · soft expiry


const FRESH_MS = 60_000;   // logical freshness
const HARD_TTL = 300;      // real Redis TTL (seconds): the safety net

export async function getPostSWR(postId) {
  const key = `post:${postId}`;
  const raw = await redis.get(key);
  if (raw) {
    const { data, freshUntil } = JSON.parse(raw);
    if (Date.now() > freshUntil) refreshInBackground(postId);  // don't await
    return data;                                                // instant, maybe a bit old
  }
  return refresh(postId);                                       // truly cold: load now
}

async function refresh(postId) {
  const data = await Post.findById(postId).lean();
  const value = JSON.stringify({ data, freshUntil: Date.now() + FRESH_MS });
  await redis.set(`post:${postId}`, value, "EX", HARD_TTL);
  return data;
}

async function refreshInBackground(postId) {
  const ok = await redis.set(`lock:post:${postId}`, "1", "PX", 5000, "NX");
  if (ok === "OK") refresh(postId).catch(console.error);      // only one refresher
}

Cache avalanche & cache penetration

          
Many keys expiring together, and requests for data that doesn't exist

        

      


      
Avalanche: thousands of keys expire in the same second

      
A stampede is about one hot key. An avalanche is many keys expiring at once. Say a deploy (or a midnight cron job) warms the cache for 10,000 products, all with EX 60. Exactly 60 seconds later, all 10,000 vanish together and the database gets hit with 10,000 queries in a single second. Then again at 120 s. A Redis restart that empties the whole cache (a cold cache) does the same thing.


      

        
ChartDB queries per second after warming 10,000 keys at t = 0

        

          

            

          

          

        

        

        

      


      
The fix is almost embarrassingly simple: add a little randomness (jitter) to every TTL so keys written together don't expire together.

      

        
lib/ttl.js


// base TTL + up to `spread` (default 20%) random extra seconds
export const withJitter = (baseSeconds, spread = 0.2) =>
  baseSeconds + Math.floor(Math.random() * baseSeconds * spread);

await redis.set(`product:${id}`, JSON.stringify(product), "EX", withJitter(3600));
// expires somewhere between 60 and 72 minutes, not all at 60:00

      

      
    
        
  • Cold cache after a Redis restart? Turn on persistence (RDB/AOF) or use a managed service with replicas, so a restart doesn't wipe everything. Warm the most important keys before sending traffic.
    • 
        
  • Protect the DB anyway. The stampede lock from Section 8 and rate limiting from Section 12 both limit how much load can reach MongoDB at once.
    • 
      


      
Penetration: asking for data that doesn't exist

      
Cache-aside only caches things it finds. If a bot (or a bug) keeps requesting /posts/<random id>, every request is a miss and every miss goes to the database, which finds nothing. Nothing gets cached, so the cache never helps. That's cache penetration.


      

        
Step-throughRequests that slip straight through the cache

        

          
        

        

          
    
            
  1. A bot requests IDs that don't exist
    A scraper loops over random IDs, or a buggy client keeps asking for a deleted post.
    2. 
            
  2. Redis misses every time
    Nothing was ever stored for these keys, because our code only caches posts it actually finds.
    3. 
            
  3. Every request reaches MongoDB
    The DB does a full lookup, finds nothing, and the result is thrown away. As far as the database is concerned, the cache isn't there.
    4. 
            
  4. Fix: cache the "not found" and validate input
    Store a small placeholder like __nil__ with a short TTL so repeats are absorbed by Redis. Reject IDs that aren't even valid ObjectIds before they reach the DB. Rate-limit clients that rack up 404s (Section 12).
    5. 
          

        

      


      

        
services/post.service.js · penetration-safe


import mongoose from "mongoose";
import { withJitter } from "../lib/ttl.js";

const NIL = "__nil__";

export async function getPost(postId) {
  if (!mongoose.isValidObjectId(postId)) return null;     // garbage never reaches the DB

  const key = `post:${postId}`;
  const cached = await redis.get(key);
  if (cached === NIL) return null;                         // known "doesn't exist"
  if (cached) return JSON.parse(cached);

  const post = await Post.findById(postId).lean();
  if (!post) {
    await redis.set(key, NIL, "EX", 30);                   // short TTL for negatives
    return null;
  }
  await redis.set(key, JSON.stringify(post), "EX", withJitter(60));
  return post;
}

      

      

        
💡

        
Keep the negative TTL short. If the post gets created a few seconds later, you don't want "not found" cached for an hour. For huge ID spaces, teams also use a Bloom filter (included in Redis 8, or Redis Stack on older versions). It answers "definitely doesn't exist" without storing every ID.

When Redis goes down

      
A cache should make the app faster, not become a new single point of failure. If Redis is unreachable, a well-written read treats it as a miss and goes to the database, and it fails fast instead of hanging.

      

        
lib/cache.js


import { Redis } from "ioredis";

export const redis = new Redis(process.env.REDIS_URL, {
  enableOfflineQueue: false,   // don't queue commands while disconnected; reject immediately
  maxRetriesPerRequest: 1,
  commandTimeout: 200,         // a cache read slower than 200 ms counts as a miss
});
redis.on("error", (err) => console.warn("redis:", err.message));

export async function cacheGet(key) {
  try {
    return await redis.get(key);
  } catch {
    return null;               // Redis down or slow → behave like a miss
  }
}

export async function cacheSet(key, value, ttl) {
  try {
    await redis.set(key, value, "EX", ttl);
  } catch {
    /* losing a cache write is fine; the DB still has the data */
  }
}

      

      

        
⚠️

        
Falling back to the DB is right, but think it through: if Redis dies during viral traffic, all of that load lands on MongoDB, which is the Section 1 crash again. Production setups add replicas with automatic failover (Sentinel, Redis Cluster or a managed service), plus rate limiting and timeouts on the DB path.

      


      
Hot keys: one key, too much traffic

      
Even Redis has limits. A single viral key always lives on one Redis node, and lakhs of GET post:42 calls per second all hit that one node's CPU and network. The fix is a tiny in-process cache (L1) with a 1–2 second TTL in front of Redis (L2). Each server then asks Redis for that key about once a second, instead of thousands of times.

      

        
lib/hotCache.js


const local = new Map(); // key -> { value, until }   (use the `lru-cache` package in production)

export async function getHot(key, ttlMs = 1000) {
  const hit = local.get(key);
  if (hit && hit.until > Date.now()) return hit.value;   // L1: process memory, ~0 ms

  const value = await cacheGet(key);                      // L2: Redis
  local.set(key, { value, until: Date.now() + ttlMs });
  return value;
}

Rate limiting Express APIs

          
One shared counter for every server, so the limit actually holds

        

      


      
The app survived the viral post. Now someone writes a script that hits POST /auth/login 500 times a second trying passwords, or scrapes /posts/:id for every ID. We need a rule like "at most N requests per time window per IP (or per user)", and anything over the limit gets 429 Too Many Requests.


      
The first version everyone writes

      

        
middleware/naiveLimit.js · don't ship this


const hits = new Map(); // ip -> { count, resetAt }

export function naiveLimit(req, res, next) {
  const now = Date.now();
  const entry = hits.get(req.ip) ?? { count: 0, resetAt: now + 60_000 };
  if (now > entry.resetAt) { entry.count = 0; entry.resetAt = now + 60_000; }
  entry.count++;
  hits.set(req.ip, entry);
  if (entry.count > 5) return res.status(429).send("Too many requests");
  next();
}

      

      
It works on your laptop, then production runs three copies of your server behind a load balancer.


      

        
Step-throughWhy an in-memory counter breaks with more than one server

        

          
        

        

          
    
            
  1. The rule: 5 requests per minute per IP
    Each server runs the naive middleware, so each one counts in its own memory.
    2. 
            
  2. The load balancer spreads traffic
    Round-robin sends request 1 to A, 2 to B, 3 to C, 4 to A… Each server only sees a third of this IP's requests.
    3. 
            
  3. The limit silently triples
    After 15 requests, every server has counted only 5, so all 15 were allowed. With 10 servers the attacker gets 50. Every deploy or restart also resets the counters to zero.
    4. 
            
  4. Fix: one counter in Redis
    Every server runs INCR rl:203.0.113.7 on the same key. Redis runs commands one at a time, so concurrent increments never get lost.
    5. 
            
  5. The limit holds everywhere
    The 6th request gets 6 back from INCR, whichever server it lands on, so the answer is 429. The key's TTL resets the window.
    6.

Fixed window with INCR + EXPIRE

      

        
INCR rl:login:<ip>
Creates the key at 1 if it doesn't exist and returns the new count.

        
EXPIRE key 60 NX
Starts the 60 s window, but only if the key has no TTL yet (first request). Needs Redis 7+.

        
count > limit → 429, else next()
When the key expires, the next request starts a fresh window at 1.

      

      

        
middleware/rateLimit.js


import { redis } from "../lib/redis.js";

export function rateLimit({ limit = 100, windowSec = 60, prefix = "rl" } = {}) {
  return async (req, res, next) => {
    const key = `${prefix}:${req.ip}`;
    try {
      const [[, count], , [, ttl]] = await redis
        .multi()
        .incr(key)                        // +1 for this request
        .expire(key, windowSec, "NX")     // start the window only on the first hit
        .ttl(key)
        .exec();                          // → [[null, 3], [null, 0], [null, 42]]

      res.set("RateLimit-Limit", String(limit));
      res.set("RateLimit-Remaining", String(Math.max(0, limit - count)));

      if (count > limit) {
        res.set("Retry-After", String(ttl));
        return res.status(429).json({ message: "Too many requests. Slow down." });
      }
      next();
    } catch (err) {
      next(); // Redis down: fail open here. For /login you may prefer to fail closed.
    }
  };
}

// usage
app.post("/auth/login", rateLimit({ limit: 5, windowSec: 60, prefix: "rl:login" }), login);
app.use("/api", rateLimit({ limit: 300, windowSec: 60, prefix: "rl:api" }));

      

      

        
⚠️

        
Why MULTI? If you send INCR and EXPIRE as two separate calls and the server crashes (or the connection drops) between them, the key exists with no TTL. That counter never resets and the user is blocked forever. MULTI … EXEC sends them as one transaction that runs together. On Redis older than 7 (no NX flag on EXPIRE), use a small Lua script instead.

      

      

        
⚠️

        
Behind Nginx, an AWS ALB or a Kubernetes ingress, req.ip is the proxy's IP unless you set app.set("trust proxy", 1). Without it, every user shares a single counter and you'll block everyone at once.

      


      
The weakness of fixed windows, and the sliding window

      

        
Step-throughThe boundary burst

        

          
        

        

          
    
            
  1. Fixed window
    The limit is 100 per minute. The counter belongs to a clock window (0:00–1:00, 1:00–2:00) and resets when a new one starts.
    2. 
            
  2. A burst just before the boundary
    A client sends 100 requests at 0:59. All allowed, count = 100. One second later the window ends and the count goes back to 0.
    3. 
            
  3. …and another just after
    100 more at 1:01, a fresh window, so all are allowed. That's 200 requests in about 2 seconds under a "100 per minute" rule.
    4. 
            
  4. Sliding window
    Instead of clock windows, count the requests in the last 60 seconds from now. At 1:01 that window holds 200 requests, so the second burst is blocked. A sorted set does this neatly.
    5. 
          

        

      


      
A sliding window log stores each request's timestamp as a sorted-set member, with the timestamp as its score. Each request removes entries older than the window, adds itself, and counts what's left.

      

        
lib/slidingWindow.js


import { randomUUID } from "node:crypto";
import { redis } from "./redis.js";

export async function slidingWindow(key, limit, windowMs) {
  const now = Date.now();
  const results = await redis
    .multi()
    .zremrangebyscore(key, 0, now - windowMs)   // 1. drop requests older than the window
    .zadd(key, now, `${now}:${randomUUID()}`)    // 2. record this request (unique member)
    .zcard(key)                                  // 3. how many are inside the window?
    .pexpire(key, windowMs)                      // 4. idle keys clean themselves up
    .exec();

  const count = results[2][1];
  return { allowed: count <= limit, count };
}

// usage: strict limit for OTP requests
const { allowed } = await slidingWindow(`rl:otp:${phone}`, 3, 10 * 60_000);
if (!allowed) return res.status(429).json({ message: "Too many OTP requests" });

      

      

        
💡

        
This version also records rejected attempts, so a client that keeps hammering stays blocked. That's usually what you want for login and OTP. It stores one entry per request, so use it for small, strict limits and keep the fixed window for high-volume API limits.

Rate limiting Socket.IO events

          
Express middleware never sees socket events, so limit them per user in Redis

        

      


      
The viral post has live comments over Socket.IO. A WebSocket is one long-lived connection. The HTTP rate limiter runs once, at the handshake, and after that every socket.emit("comment:new", …) flows through the open socket without touching Express. One script can open a socket and emit 1,000 comments a second, flooding every viewer in the room.

      
    
        
  • Limit events, not just connections. Use socket.use(), which runs for every incoming packet on that socket.
    • 
        
  • Key by user, store in Redis. The same user can open three tabs, and the load balancer may send each tab to a different server. Per-process counters would let them send three times the limit.
    • 
        
  • Also limit handshakes per IP with io.use(), so nobody can open thousands of sockets.
    •

// npm i rate-limiter-flexible
import { RateLimiterRedis } from "rate-limiter-flexible";
import { redis } from "../lib/redis.js";

const commentLimiter = new RateLimiterRedis({
  storeClient: redis,
  keyPrefix: "rl:socket:comment",
  points: 5,       // 5 comments…
  duration: 4,     // …per 4 seconds, per user
});

io.on("connection", (socket) => {
  const userId = socket.data.userId;            // set by your auth middleware in io.use()

  socket.use(async ([event], next) => {
    if (event !== "comment:new") return next();  // only limit what needs it
    try {
      await commentLimiter.consume(userId);       // rejects when out of points
      next();
    } catch (rej) {
      if (rej instanceof Error) return next();    // Redis error → let it through
      socket.emit("rate_limited", { event, retryAfterMs: rej.msBeforeNext });
      // not calling next() drops this packet
    }
  });

  socket.on("comment:new", (comment) => {
    io.to(`post:${comment.postId}`).emit("comment:added", comment);
  });
});

Socket.IO across many servers

          
Redis Pub/Sub carries broadcasts between servers, and sets and hashes store presence

        

      


      
One Socket.IO server can't hold every live viewer of a viral post, so you run two or more. Here's the catch: each server only knows the sockets connected to it. io.to("post:42").emit(…) on server 1 reaches server 1's sockets and nobody else.


      

        
Step-throughA live comment that only half the room sees

        

          
        

        

          
    
            
  1. Two servers, one room
    The load balancer put Alice and Bob on server 1, and Charlie and Dia on server 2. All four joined the room post:42 for live comments.
    2. 
            
  2. Alice comments, and half the room misses it
    Server 1 runs io.to("post:42").emit(…). The default in-memory adapter only knows local sockets, so Bob gets it and Charlie and Dia don't.
    3. 
            
  3. Plug in the Redis adapter
    Each server opens two Redis connections: one to publish and one to subscribe. Both subscribe to the adapter's channels.
    4. 
            
  4. Server 1 delivers locally and publishes
    Alice comments again. Server 1 sends it to Bob as before, and publishes the packet to Redis.
    5. 
            
  5. Redis fans it out
    Redis pushes the message to every subscribed server. Server 2 receives it and emits to its own sockets in post:42, Charlie and Dia. Everyone sees the comment, and your emit code didn't change.
    6. 
          

        

      


      

        
Key Concept

        
Pub/Sub: PUBLISH channel message delivers the message instantly to every connection that ran SUBSCRIBE channel. It's fire-and-forget. Nothing is stored, so a server that's offline at that moment misses the message.

        
A connection in subscribe mode can only run Pub/Sub commands. That's why the adapter needs a second client, made with pubClient.duplicate().

The Socket.IO Redis adapter

// npm i socket.io @socket.io/redis-adapter ioredis
import { createServer } from "node:http";
import { Server } from "socket.io";
import { createAdapter } from "@socket.io/redis-adapter";
import { Redis } from "ioredis";
import app from "./app.js";

const pubClient = new Redis(process.env.REDIS_URL);
const subClient = pubClient.duplicate();       // subscriber mode needs its own connection

const httpServer = createServer(app);
const io = new Server(httpServer, {
  adapter: createAdapter(pubClient, subClient),
});

io.on("connection", (socket) => {
  socket.on("post:join", (postId) => socket.join(`post:${postId}`));
  socket.on("comment:new", (c) => {
    io.to(`post:${c.postId}`).emit("comment:added", c); // now reaches EVERY server
  });
});

httpServer.listen(process.env.PORT ?? 3000);

Socket.IO can start with HTTP long-polling before upgrading to WebSocket, and those polling requests must reach the same server, or you'll see HTTP 400 "Session ID unknown". A background worker without a Socket.IO server can emit events through Redis with @socket.io/redis-emitter.

      


      
Central storage: who's online right now?

      
The adapter only relays messages. It doesn't give your REST API an answer to "how many people are watching?" or "is user 9 online?". Keep that state in Redis yourself with a hash (sockets per user, since one user can have several tabs) and a set (online users).

      

        
socket/presence.js


io.on("connection", async (socket) => {
  const userId = socket.data.userId;

  // count this user's open sockets (tabs, phone + laptop…)
  const tabs = await redis.hincrby("presence:sockets", userId, 1);
  if (tabs === 1) await redis.sadd("online:users", userId);   // first socket → online

  socket.on("disconnect", async () => {
    const left = await redis.hincrby("presence:sockets", userId, -1);
    if (left <= 0) {
      await redis.multi()
        .hdel("presence:sockets", userId)
        .srem("online:users", userId)
        .exec();
    }
  });
});

// anywhere: a REST route, another server, a cron job
const onlineCount = await redis.scard("online:users");              // 1284
const isOnline = await redis.sismember("online:users", userId);     // 1 or 0

      

      

        
⚠️

        
If a server crashes, its disconnect handlers never run, and those users look online forever ("ghost users"). Production setups add a heartbeat: each server refreshes a key like presence:server:<id> with a short TTL and cleans up users belonging to servers whose key expired. Or each user gets presence:user:<id> with EX 60, refreshed by a client ping.

Real-time leaderboards with sorted sets

          
Millions of scores, always ranked, updated in O(log N)

        

      


      
Kodr runs a weekly coding contest: 50,000 participants, scores changing every few seconds, and everyone refreshing to see the top 10 and "my rank". In SQL, "my rank" is SELECT COUNT(*) + 1 FROM scores WHERE score > :myScore. That runs on every refresh, for every participant, while scores keep changing underneath it. It's fine for 500 users and painful for 50,000.


      

        
Key Concept

        
A sorted set keeps unique members ordered by score at all times. Internally it pairs a skip list (for ordering) with a hash table (for member → score lookups). Redis never "sorts" when you ask for the leaderboard, because it's already sorted.

        
ZINCRBY · ZREVRANK · ZSCORE cost O(log N) or better. Top-10 with ZRANGE … REV costs O(log N + 10). With 50,000 members, log₂ N is about 16 steps.

The API

      

        
routes/leaderboard.routes.js


import { Router } from "express";
import { redis } from "../lib/redis.js";

const router = Router();
const LB = "lb:contest:42";

// flat [member, score, member, score…] → [{ rank, userId, score }]
const toRows = (flat, startRank = 1) => {
  const rows = [];
  for (let i = 0; i < flat.length; i += 2) {
    rows.push({ rank: startRank + i / 2, userId: flat[i], score: Number(flat[i + 1]) });
  }
  return rows;
};

// a user solved a problem
router.post("/score", async (req, res) => {
  const { userId, points } = req.body;
  const total = await redis.zincrby(LB, points, userId);      // "410" (a string)
  res.json({ userId, total: Number(total) });
});

// top N, highest first
router.get("/top", async (req, res) => {
  const limit = Math.min(Number(req.query.limit) || 10, 100);
  const flat = await redis.zrange(LB, 0, limit - 1, "REV", "WITHSCORES");
  res.json(toRows(flat));
});

// my rank + the 2 people above and below me
router.get("/me/:userId", async (req, res) => {
  const { userId } = req.params;
  const rank = await redis.zrevrank(LB, userId);              // 0-based, or null
  if (rank === null) return res.json({ rank: null });

  const start = Math.max(0, rank - 2);
  const [flat, score] = await Promise.all([
    redis.zrange(LB, start, rank + 2, "REV", "WITHSCORES"),
    redis.zscore(LB, userId),
  ]);
  res.json({ rank: rank + 1, score: Number(score), around: toRows(flat, start + 1) });
});

export default router;

Production checklist

      

        
One client per process
Import it everywhere. Create a duplicate() only for subscribers.

        
Every cache key has a TTL, with jitter
No "forever" cache entries. A plain SET wipes the TTL.

        
Set maxmemory and a policy
Keep pure cache separate from counters, sessions and leaderboards.

        
Invalidate on write: update the DB, then DEL
Know which keys each write affects.

        
Protect hot keys
Lock with SET NX PX, single-flight, optional L1 cache.

        
Fail fast, fall back
commandTimeout, enableOfflineQueue: false, try/catch around cache calls.

        
Atomic multi-step logic
MULTI/EXEC or Lua for anything like "INCR then EXPIRE".

        
No KEYS *, no huge values

Real client IPs

Lock it down
Password/ACL, TLS on managed services, never exposed to the internet (security groups).

Hit ratio, memory, evictions (evicted_keys) and the slow log.
